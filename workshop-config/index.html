Mission briefing

The story. The v2.3.0 platform deploy didn't just touch application code — it "standardized" the IBM Bob configuration on every developer machine. Since this morning, Bob's answers in the Merchant Help Center workspace have been unreliable: files it cannot see, policies it quotes from memory, standards that contradict the code.

The platform team kept a last known-good snapshot of the pre-deploy configuration — it is in lab/backups/. You are the engineer on call. Five configuration defects stand between Bob and reliability. Restore them, collect one letter per challenge, and together the letters spell the winning word that completes the mission.

What "restored" means (the verification script encodes exactly this):
  • A challenge is solved when its live configuration file is byte-identical to the matching file in lab/backups/ — copy the backup over the live file.
  • Each backup file belongs at exactly one live location. The official IBM Bob configuration docs describe where every kind of file lives.
  • Deleting or hand-rewriting a poisoned file is not a restore.
Rules of engagement. You may change only the five live configuration locations the challenges point at, and only by restoring from lab/backups/. Protected (do not edit): lab/verify.mjs, lab/backups/, lab/docs/, lab/src/, lab/README.md, lab/AGENTS.md. Deliverables: five green challenges and the winning word.

If Bob cannot read files at all, that is not a failure of the prompt — it is your first symptom. Start with Challenge 1.

The five challenges below are ordered as a diagnostic cascade: with all five defects live, Challenge 1's symptom dominates, and each restore reveals the next symptom. You may tackle them in any order.

Symptom. Ask Bob to read any project file. Bob cannot — not just one file, any file. Something has redefined what Ask mode can do.

7Debrief (53–60 min)

  • Configuration is context: Bob's reliability is a function of its configuration, not just the model. Five wrong lines made every answer suspect.
  • Where config lives: .bob/rules/ (all modes) vs .bob/rules-{mode}/ (one mode) vs AGENTS.md (auto-loaded) vs .bob/custom_modes.yaml (mode definitions — they can override the built-in modes) vs .bobignore (access) vs .bob/settings.json (hooks).
  • A mode with no tool groups has no tools. When a mode "can't" do something, check its definition before blaming the model.
  • .bobignore is human-in-the-loop by design: Bob cannot edit it, so access rules are the operator's responsibility.
  • Hooks inject context: when answers look systematically biased, audit .bob/settings.json — Bob may be being lied to behind its back.
  • Not every config file was a bug: AGENTS.md was healthy all along.
