Mission briefing

The story. Settlement Desk is the batch job that pays KKP merchants every day. Yesterday's v2.3.0 deploy was meant to "simplify" the payout math. This morning three merchants called support:

  • SYN-A1 was paid twice for the same sale.
  • SYN-A2 was paid for transactions that do not belong to the settlement day.
  • SYN-B1's payout does not match its ledger total — it is off by a single satang.

You are the on-call engineer. You have 60 minutes, a terminal, and IBM Bob. Fix the three challenges and collect one letter per challenge — together the letters spell the winning word that completes the mission.

Business contract (the acceptance tests encode exactly this):
  • A transaction id settles at most once — the first occurrence wins.
  • Only transactions inside the 22 Oct 2026 Bangkok business day settle: 2026-10-21T17:00:00.000Z (inclusive) to 2026-10-22T17:00:00.000Z (exclusive). ICT is UTC+7.
  • Payouts are exact to the satang. Amounts arrive as baht strings, e.g. "1500.00".
  • Non-positive amounts never settle.
Rules of engagement. You may edit only lab/server.mjs. Protected (do not edit): lab/test/, lab/data.json, lab/verify.mjs. Deliverables: repaired code, all 5 acceptance tests green, and the winning word.

2Investigate with Bob — Ask mode (8–23 min)

In IBM Bob, switch to Ask mode. Ask analyzes and explains — it does not edit files. Paste this prompt (adapt it as you like):

IBM Bob · Ask mode
Read these files in my workspace: lab/server.mjs, lab/data.json and lab/test/settlement.test.mjs.

Context: after yesterday's v2.3.0 deploy of our Settlement Desk, merchants report three symptoms:
1. SYN-A1 was paid twice for the same transaction.
2. SYN-A2 was paid for transactions that do not belong to the 22 Oct 2026 Bangkok business day.
3. SYN-B1's payout does not match its ledger total in satang.

Task: compare what processSettlements actually does against each acceptance test. For every
failing test, give me one hypothesis, the exact code lines and data records that support it,
and what a minimal repair would have to guarantee. Do not edit any files.

While you read Bob's analysis, answer these for yourself:

What evidence distinguishes a data problem (bad records) from a processing problem (bad code)?

Which records does the loop actually accept? Which ones should it reject — and by which contract rule?

For SYN-B1: what does 555.55 + 1555.55 + 2555.62 actually equal in JavaScript, and why?

IBM Bob · Agent mode

4Verify, collect your letters, and win (43–53 min)

Each repaired challenge reveals one letter. Check your progress any time:

terminal

npm run verify   # each repaired challenge reveals a letter

When all three challenges pass, your three letters spell the winning word. Enter it below to complete the mission.

Mission accomplished — the Settlement Desk pays correctly again

All payouts are idempotent, inside the business day, and exact to the satang. Keep your terminal history and the approved diff ready — the facilitator will review them in the debrief.

5Debrief (53–60 min)

  • Three symptoms, one deploy, three distinct defects — and one odd record (a zero-amount transaction) that was never a bug. Symptom ≠ cause.
  • Why payments code computes in integer satang, not decimal floats.
  • How you used Bob: Ask built hypotheses against evidence; Agent proposed a diff that you approved. Bob's explanation was never the proof — the executed tests were.

Stuck? Hints

Hint 1 — a nudge

Run npm start and compare each merchant's total with the value its failing test demands. Then ask three questions about every record the loop accepts: Have I seen this transaction id before? Is its timestamp inside the business-day window? What exact number does its amount become in memory?

Hint 2 — a stronger nudge (last resort)

There are three independent defects: that the loop has no memory of which transaction ids it has already settled; that no timestamp is ever compared to the window bounds; and that amounts are handled as decimal floats before a final truncation. In a Node REPL, evaluate 0.1 + 0.2, then 555.55 + 1555.55 + 2555.62. Ask Bob why the results are not exact, and what representation payment code should use instead.
