00:00

Mission briefing

The story. Settlement Desk is the batch job that pays KKP merchants every day. Yesterday's v2.3.0 deploy was meant to "simplify" the payout math — and it also "standardized" the IBM Bob configuration on every developer machine. This morning, everything looks broken twice over:

  • The payouts are wrong. Three merchants called support: SYN-A1 was paid twice for the same sale, SYN-A2 was paid for transactions outside the settlement day, and SYN-B1's payout is one satang short.
  • Bob itself is unreliable. It cannot read files, quotes policies from memory, and recommends standards that contradict the code — the assistant you would normally investigate with is part of the incident.

The platform team kept a last known-good snapshot of the pre-deploy configuration — it is in lab/backups/. You are the engineer on call: restore Bob first, then — with an assistant you can trust — fix the Settlement Desk. Eight challenges, one letter each. Your Part 1 letters spell one winning word; your Part 2 letters spell another.

Part 2 business contract (the acceptance tests encode exactly this):
  • A transaction id settles at most once — the first occurrence wins.
  • Only transactions inside the 22 Oct 2026 Bangkok business day settle: 2026-10-21T17:00:00.000Z (inclusive) to 2026-10-22T17:00:00.000Z (exclusive). ICT is UTC+7.
  • Payouts are exact to the satang. Amounts arrive as baht strings, e.g. "1500.00".
  • Non-positive amounts never settle.
What "restored" means in Part 1 (the verification script encodes exactly this):
  • A challenge is solved when its live configuration file is byte-identical to the matching file in lab/backups/ — copy the backup over the live file.
  • Each backup file belongs at exactly one live location. The official IBM Bob configuration docs describe where every kind of file lives.
  • Deleting or hand-rewriting a poisoned file is not a restore.
Rules of engagement. In Part 1 you may only restore the five live configuration locations from lab/backups/. In Part 2 you may edit only lab/server.mjs. Protected (do not edit): lab/test/, lab/data.json, lab/verify.mjs, lab/backups/, lab/docs/, lab/src/, lab/AGENTS.md, lab/README.md. Deliverables: all 8 challenges green and the two winning words.

9Debrief (56–60 min)

  • Two incidents, one deploy: the payout code was broken and the assistant was compromised. When your tools are suspect, fix the tools before trusting their output.
  • Configuration is context: five wrong lines in .bob/ made every Bob answer suspect — mode-specific rules, general rules, mode definitions, file access, hooks.
  • A mode with no tool groups has no tools; .bobignore is human-in-the-loop by design (Bob cannot edit it); hook output is injected context — audit .bob/settings.json when answers look systematically biased.
  • Three payout symptoms, three distinct code defects — and oddities that were never bugs: a zero-amount transaction, and AGENTS.md, which was healthy all along.
  • Why payments code computes in integer satang, not decimal floats.
  • Bob's explanation was never the proof — the executed tests and byte-exact restores were.

★ Bonus — Ponytail A/B: see what a skill changes (10 min, optional)

The mission is over, Bob is trustworthy, and the Settlement Desk pays correctly. Now put that repaired desk to work: the same coding task, run twice — once without a skill, once with one — and measure the difference. The skill is ponytail (MIT): it puts the agent in "lazy senior dev" mode — the smallest change that fully solves the task, no abstraction, options or boilerplate nobody asked for.

Setup (2 min)

Everything lives in the bonus/ folder next to this guide. It contains the repaired Settlement Desk — the exact code you finished in Part 2 — plus a new ticket from Finance in bonus/lab/TASK.md.

terminal (from workshop-developer/)
cd kkp-workshop/workshop-developer   # from the folder containing the repo
cp -r bonus/lab run-a        # run A: no skill
cp -r bonus/lab run-b        # run B: with ponytail
mkdir -p run-b/.bob/skills
cp -r bonus/skills/ponytail run-b/.bob/skills/ponytail

Run A — plain Bob (3 min)

Open run-a/ in Bob, start a new session, and paste the ticket text from TASK.md as-is. When Bob finishes:

  • write down the session's token usage (Bob shows it per session),
  • run bonus/measure.sh run-a and note lines added, files touched, new dependencies.

Run B — Bob with ponytail (3 min)

Open run-b/ in Bob (the skill sits in .bob/skills/), start a new session so the skill loads, say "ponytail" once, then paste the same ticket. Record the same numbers, then compare:

Same model, same correct output — both tools flag SYN-A2 (10 baht short) and SYN-C1 (paid but never settled), compare money exactly in satang, and exit 1. Without the skill the agent produced 3.1× the code; even counting the skill's own text as a cost, its session churned ~30% less context and made fewer API calls. The ponytail run also ended the way the skill demands: naming what it skipped (a real CSV parser) and the one risk that carries (quoted fields would misparse). Record your own numbers from Bob's session token usage and see how yours compare.

Debrief question: the ticket looks like a tool — CSV input, matching, reporting, exit codes — and a plain agent often builds one: a CSV parser module, a matching engine, tolerance config, report classes. The whole job fits in one new file of roughly thirty lines that reuses what the desk already has: processSettlements computes the desk side, toSatang keeps money exact, and the "CSV" is two columns split on a comma. A skill does not make the agent smarter; it changes which option the agent reaches for first. Fewer lines means fewer tokens, fewer files to review, and less surface for the next incident.

Stuck on Part 2? Hints

Hint 1 — a nudge

Run npm start and compare each merchant's total with the value its failing test demands. Then ask three questions about every record the loop accepts: Have I seen this transaction id before? Is its timestamp inside the business-day window? What exact number does its amount become in memory?

Hint 2 — a stronger nudge (last resort)

There are three independent defects: that the loop has no memory of which transaction ids it has already settled; that no timestamp is ever compared to the window bounds; and that amounts are handled as decimal floats before a final truncation. In a Node REPL, evaluate 0.1 + 0.2, then 555.55 + 1555.55 + 2555.62. Ask Bob why the results are not exact, and what representation payment code should use instead.
